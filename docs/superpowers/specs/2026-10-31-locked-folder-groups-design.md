# Locked folder groups: design

## Intent

Locked currently shows every locked photo in one flat timeline. The owner keeps three kinds of material there: sensitive documents (bank cards), sexually explicit photos, and emotionally sensitive photos. They want to keep these apart so that opening Locked does not put everything in front of them at once.

The solution is named groups that exist only inside Locked, working like albums restricted to locked assets.

## Goals

- A user can create, rename and delete groups in Locked.
- A user can add locked photos to groups and remove them. A photo can be in several groups (most are in one).
- The Locked page has a toggle: all locked photos, or only ungrouped locked photos.
- Opening a group shows its photos in a timeline like the Locked page.
- Groups and their contents are only reachable after the existing Locked PIN unlock. No separate lock.
- Deleting a group never deletes or unlocks its photos.

## Non-goals

- Nested groups. One flat level only.
- Mobile app UI. The mobile app is left as-is; server changes must be additive so it keeps working unchanged.
- Sharing groups, shared links, partners, or any exposure outside the owner.
- Extra locking per group.

## Anti-goals

- A group, its name, its cover or its photo count must never be visible outside an unlocked Locked session: not in album lists, search, memories, explore, tags, sync streams, or API responses reachable without Locked auth.
- Photos must never leak out of Locked as a side effect (for example, via a group being treated as an album).
- Moving a photo out of Locked (visibility change) must not leave a stale group membership that exposes it.

## Constraints

- Follows the repo rules in `AGENTS.md`, `server/AGENTS.md` and `web/AGENTS.md`: zod DTOs, `@Authenticated` and `@Endpoint` on routes, `requireAccess` before touching a resource, repositories as the only I/O layer, a generated migration, regenerated OpenAPI clients and SQL snapshots, `i18n/en.json` keys, no code comments.
- The mobile Dart client is regenerated by `mise //:open-api`; new endpoints are additive, so no backward-compatibility patch should be needed.
- Authorization for the new endpoints must require the same elevated Locked session as the existing locked asset access (builder: find how that is enforced today and reuse it).

## Decisions made with the owner

- Many-to-many between groups and assets.
- Flat, web only, no extra lock, toggle between all and ungrouped only.

## Direction (assistant's call, builder may adjust)

- New tables for the group (owner, name, timestamps) and the group-asset join, modeled on the existing album and album-asset tables but with no sharing columns. A separate concept from albums, not an album flag, so existing album queries cannot leak locked groups.
- A dedicated controller for group CRUD and membership. Adding an asset requires it to be owned and currently Locked visibility. If an asset's visibility leaves Locked, its memberships are removed.
- The group timeline reuses the time-bucket endpoints by adding a group filter that implies Locked visibility. The "ungrouped only" toggle is a filter on the same endpoints.
- Web: a group strip or sidebar on the Locked page with a create button, a group route under `locked/`, selection actions "Add to group" (a modal) and "Remove from group", and the all/ungrouped toggle. Strings in `i18n/en.json`.
- Considered and rejected: reusing tags (tags are visible in tag views and search, so they could expose group names) and reusing albums (shared and listed everywhere).

## Left to the builder

- Table and column naming, endpoint paths, DTO shapes, and exact UI layout within the web conventions.
- Whether to add medium and e2e tests beyond unit and controller specs (expected: yes for the visibility-leak cases).
- Handling of deletion paths (user deletion, asset deletion) via cascades.

## Success

A user unlocks Locked, creates "Cards" and "Private", puts photos in them, toggles to ungrouped to see what is left, and nothing about the groups is visible anywhere else in the app or API without that unlock.
